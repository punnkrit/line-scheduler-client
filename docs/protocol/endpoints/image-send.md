# Native still-image send contract

## Current CLI status

Encrypted native JPEG/still-PNG photos use the single-representation format
below. Letter Sealing is required by default and always required for groups.
Real-V2 and independent WebCrypto recipient tests pass. Server acceptance and
actual LINE-app display of the larger preview remain unverified by a live send.

## Preparation and limits

`pp`, `Dk`, `CP`, `Lk`, `Rk`, `Ik`, `qk`, and `kk` establish:

- Chrome accepts JPEG, PNG, GIF, and BMP based on its picker/type checks, with
  a 20 MiB image-input threshold. Original mode has a 100-million-pixel limit.
- Ordinary images are converted to JPEG at quality 0.6. The scale factor is
  `min(1, sqrt(1280*1280/(width*height)))`, with floored output dimensions.
- A separate JPEG preview fits within 384×384 without enlargement, rounded
  dimensions, at quality 0.3. Canvas uses a white background.
- Original/animated media take a separate `MEDIA_CONTENT_INFO` path.

The CLI deliberately accepts only JPEG and still PNG (actual decoded content,
not suffix), at most 20 MiB, 40 million decoded pixels, and 16384 pixels on either
axis. Decode configuration is checked before allocating the decoded image, then
full decoding must succeed. PNG `acTL` rejects animation. GIF/BMP/WebP and original
mode are outside this milestone. EXIF orientation is applied, metadata is removed,
and JPEG bytes plus a preview are prepared before session access. Browser and Go
JPEG encoders/resampling differ; byte parity is not claimed. These resource limits
are CLI policy, not claimed server limits. Use generic `--file` for original bytes.

## Capability and dispatch

`LA.checkAndNegotiate`, `LA.checkAndGetMediaMessageFlow`, `lU`, and `ZU` establish
`TalkService/determineMediaMessageFlow` with arguments `[{"chatMid":"CHAT"}]`.
The success data has a `flowMap` keyed by decimal content type; image key `"1"`
returns 1 (plaintext) or 2 (encrypted). Chrome caches this with `cacheTtlMillis`.
The CLI reads it fresh for each image send with session read recovery. Missing,
malformed, unknown flow or transport failures stop the send. It permits plaintext
only for explicit flow 1, an explicitly non-E2EE session, or the existing explicit
Letter Sealing-unavailable signals. Flow 2 retains normal peer/group key validation
and complete membership before any required group registration. No failure of a
key, registration, upload, or send triggers plaintext fallback or mutation replay.

`qC` (enqueueFileMessages), `sP`, `kP`, `PP`, `jP`, `VP`, `UP`, and `MP` establish:

| Stage | Encrypted image (flow 2) | Plain image (flow 1) |
| --- | --- | --- |
| Prepare | Resolve valid peer/group encryption keys | Explicit capability evidence |
| Full upload | POST `/r/talk/emi/reqid-UUID` | After message creation |
| Preview upload | POST `/r/talk/emi/OID__ud-preview` | Generated by server; no client preview upload |
| Message | `sendMessage` with content type 1, `hasContent=true`, encrypted payload | `sendMessage` with content type 1, `hasContent=true` |
| Plain upload | Not used | POST `/r/talk/m/MESSAGE_ID`, OBS type `image` |

`VP` supplies base64 JSON `X-Obs-Params` with `ver=2.0`, a name, and type `file`
for encrypted bytes or `image` for plain images. Uploads use the encrypted OBS
access token and Chrome application headers. The full encrypted upload must
return `x-obs-oid`; absence is an unknown upload outcome and prevents later steps.
The preview must succeed before sending. There is no upload retry/resume in the
CLI, even though Chrome has UI retry facilities.

Chrome `CL` uses the same 32-byte key material and restarts FileEncryption
HKDF/AES-CTR for the full and smaller preview. That creates a two-time stream
when the plaintexts differ. This fork deliberately uses **one representation**:

1. Prepare the bounded normalized full JPEG using the existing limits.
2. Generate fresh 32-byte random key material and encrypt it exactly once.
3. Upload that exact ciphertext-plus-HMAC buffer as both the `emi` full object
   and `OID__ud-preview`. Never independently encrypt another thumbnail.
4. Advertise the actual normalized JPEG dimensions in `MEDIA_THUMB_INFO`, and
   its byte length in `FILE_SIZE`. Keep key material and filename exclusively
   in the authenticated Letter Sealing payload; outer `e2eeVersion` remains 2.

The version-matched Chrome download path (the function containing the
`E2EE_HMAC_NOT_MATCHED` check) applies the same HKDF, counter and HMAC verification
to the preview and full resource. The resource URL builder chooses the `__ud-preview` suffix; neither
path requires a different key or resized plaintext. An independent Node WebCrypto
recipient authenticates and decrypts both generated objects byte-for-byte, and a
real Letter Sealing V2 recipient independently opens the key payload. This is
source-level and synthetic compatibility evidence; it does not prove OBS accepts
the larger preview or that every LINE app renders it. No live traffic was captured.

Identical ciphertexts reveal that the representations are equal, which is
intentional. They do not expose an XOR of *different* images. Independent random
key material is generated for every photo, including repeated copies of a photo.
The cost is a larger preview download; JPEG quality/dimensions follow existing
normalization. The distinct prepared thumbnail is never encrypted or uploaded.

The CLI persists the message request sequence before `sendMessage`; OBS uses its
own random request ID, and the preview reuses the returned object ID. Outcomes
record `attachment_upload`, `preview_upload`, and `send` independently. A plain
image message already created remains confirmed if upload fails. Missing/lost
message receipts remain unknown. Success returns the established send receipt
with message/chat IDs, request sequence, and encryption status; no image keys,
chunks, object IDs, or raw server bodies are printed.

## Reply boundary

Chrome's compose handler adds reply relation fields to `enqueueTextMessage` and
`enqueueStickerMessage`, but calls the file/image enqueue path separately. `qC`
and `sP` construct media messages without a relation. This does **not** establish
server rejection or acceptance of image reply fields. The CLI therefore rejects
`--image --reply-to` before session access instead of claiming unverified support.
Text replies and existing generic-file behavior are unchanged. Text/stdin/file,
mentions, and image inputs cannot be combined.

## Security restriction (2026-10-18)

The encrypted native-image send path is disabled before uploads, group-key
registration, or sequence reservation. Reinspection of the version-matched
package above confirmed `_L` deterministically derives a counter and `CL`
restarts AES-CTR with it for each object. The full image and preview therefore
share a keystream. No independent preview nonce/key or compatible secure
representation was established. Receiving historical images is unchanged.
Do not restore encrypted sends until both sender and recipient semantics of a
secure representation are verified. Plaintext capability handling is separate.

## Single-representation recovery and grouping (2026-10-21)

The original distinct-thumbnail encrypted path above remains prohibited. The
single-representation upload replaces it, retaining mandatory E2EE capability,
peer/group key checks, persisted sequences, fenced saves and no mutation retry.

Reinspection of public Chrome 3.7.2 `NP`, `RP`, `LP`, `jP` and `UP` establishes:
consecutive image selections are split with `chunk(images,10)`; singleton tails
are ungrouped. A group uses decimal-string `GSEQ` (1-based), `GTOTAL` (2..10),
and initial `GID="0"`. The server receipt supplies the real opaque `GID` (not assumed numeric); later photos
use that confirmed value. Each new group starts again with `GID="0"`. Uploads
and sends run sequentially. The fork never invents an ID or continues after a
missing/mismatched group ID, failed upload, missing receipt or uncertain send.
`SendImagesContext` and repeated CLI `--image` return confirmed receipts on error.
The scheduler durably saves progress before another photo and never replays a
claimed batch. Tests cover counts 1,2,10,11,20,21,50 and interrupted groups.
